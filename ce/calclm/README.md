# CalcLM M4: on-calculator inference

> The v2.2 and v2.3 release sections below describe calculator bundles that were never
> published. They are records of the device releases, not install instructions.

`CALCLM.8xp` runs the CalcLM ternary transformer natively on a TI-84 Plus CE (eZ80, 48 MHz)
and writes TI-BASIC programs. The inference core reproduces `model/intref.py` bit for bit:
tested token for token in CEmu on the shipping export `runs/v1/export` and on `runs/v0/export`
(export format 1, learned positions), and on `runs/v2/export` (format 2: ALiBi, a 256-token
sliding window over a ring K/V cache, generation up to 1024 tokens, the tracker's logit masks;
the shipped v2 model, S0 seed 10, see "v2" below). One program runs both formats.
Install instructions: INSTALL.md (in the private research record). The v2.3 release candidate, built for the wide
model shape W, is described in "v2.3" below and INSTALL-v2.3.md (in the private research record).

| `core/ez80/*.s` | eZ80 assembly hot loops: scale_out, quant_vec, RMSNorm/SwiGLU products, attention (scores, softmax, P.V, head average), SiLU, peak scans, P.V compaction |

| `tools/gen_kernels.py` | the two M2 kernels (`ce/kernel/gen_tmv.py`, unchanged) for G = 39 and 103 |

| `test/drv.c` | test/benchmark driver (host shared library and CEmu flat binary) |

benchmark `ce/tools/clm_bench.py`.

### LD2 decoder in v2.2

`core/clm_ld2.c` implements `model.linker.ARMS["LD2"]`: label binding, no early EOS,
the deadline with BODY 24, the XT exit ledger, Row's R1/R2 closure, and the full-vocabulary
T 1.0 stop hazard. Hazard products and division use uint64; the extra xorshift draw occurs
before the ordinary T 0.8 / top-20 draw, even when the hazard is zero. Forced tokens consume
neither draw. Row skips BOS, matching `row_bos_fix=True`.

The OS program enables LD2 after each load when a format 2 model has a compatible tracker
vocab and an archived, matching `CLMLD2` AppVar. `clm_program_decoder` restores horizons and
attempts the optional offset load. Missing, unarchived or rejected offsets retain v2.1's
decoder and RAM/context budget. The title adds `ld2` when active, and remains within 40
columns even for vocab 1024. Turning masks off or choosing greedy temporarily disables LD2;
returning to sampled generation with masks restores it. Caps remain at most 1024 including
BOS. Format 1 behaves as before.

`clm_load` still clears horizons, LD2 and its workspace pointer. Core users can call
`clm_ld2_load(&M, workspace, payload, size, export_sha)` after loading, supply the six-byte
export SHA from their accepted CLMVOC, and then enable horizons and LD2 before
`clm_reset(..., masks=1)`. `clm_program_decoder` applies those program defaults in one call.
Reset clears decoder state while retaining E. The caller owns the 2,652-byte workspace.

CLMLD2 version 2 has an 83-byte payload, all integers little-endian:

| Offset | Bytes | Meaning |
|---|---|---|
| 0 | 4 | `LD2` and version 2 |
| 4 | 2 | vocabulary size |
| 6 | 3 | model blob size |
| 9 | 6 | export SHA-256 prefix, the same bytes as CLMVOC offsets 9..14 |
| 15 | 64 | 16 uint32 E values |
| 79 | 4 | FNV-1a of bytes 0..78, including E |

The on-device binding checks the loaded vocabulary and blob size, compares CLMVOC's export
SHA prefix, and checks the small payload's checksum. The CLM slice layout was already
validated by `clm_load`. Version 1 offsets are rejected; regenerate CLMLD2 with the command
below. The shared post-load decoder check takes 168,814 CEmu cycles with LCD DMA on, or
0.003517 seconds at 48 MHz. The full SHA-256 check remains in the host packager, which
compares model.bin with both model.json and the fit's recorded hash.

This follows the existing export identity convention rather than hashing the calculator's
weights. CLM headers check slice continuity, and CLMVOC checks vocabulary/blob size; neither
proves that every weight byte matches its claimed export. CLMVOC's six-byte SHA was
previously display-only. The cheap binding now uses it, but cannot detect swapped weights
with an identical layout paired with a misleading CLMVOC. FNV-1a detects accidental payload
corruption; it is not an authentication scheme.

The wired build is 61,075 bytes uncompressed. The standard CE toolchain ZX7 compression
produces a 33,130-byte CALCLM.8xp; runtime code expands to its original size. BSS is 60,326
of 60,690 bytes, including one extra linker alignment byte compared with the previous build.
The LD2 workspace is appended to CLMTMP after the V cache, never added to BSS or VRAM.
The free gap after activations is only 1,903 bytes, smaller than the workspace.

The checked-in fit is `ce/tests/fixtures/ld2_offsets_full.json`, reused from E2b's
`runs/e2b/S0-s10/offsets_full.json`: 2,000 train programs, horizons, full T 1.0 weights.
The only added field is the shipped model's `export_sha256`,
`2877c31fb754dd9b70d62134e81daf05fd5e4b1bc893ed4970edfecc8956b54d`.
The packager checks that field against both model.bin and model.json, and rejects fits
without horizons or full-vocabulary hazard weights:

```sh
uv run python -m ce.calclm.tools.make_ld2 \
  --export runs/v2/export --offsets ce/tests/fixtures/ld2_offsets_full.json \
  --out ce/build/CLMLD2.8xv
```

This creates a review artifact; it does not change the installation bundle. The test driver
exposes `LD2` to toggle the core flag, `E` to copy trusted raw offsets, `LD2_LOAD` to validate
the version 2 payload and `PROGRAM_DECODER` to run the same post-load policy as the OS
program. HostCore/EmuCore expose `set_ld2`, `load_E`, `load_ld2` and `program_decoder`.
`ce/tests/test_calclm_os.py` links the actual OS model.c with fileioc/RAM stand-ins; emulator
parity uses the shared policy and the exact core.o. Neither path launches the GUI in TI-OS.

Measure whole programs with and without `--ld2`:

```sh
uv run python -m ce.tools.clm_bench \
  --v2 --flash --program 1 --cap 1024 --masks --horizons --ld2 \
  --json ce/build/ld2_seed1.json
```

`--ld2` requires `--v2 --masks --horizons --program SEED`. `--ld2-offsets` selects another
fit bound to that export. `--json` also saves whole-program measurements, with the exact
filename supplied. The JSON records the model hash, LD2/horizons flags, and the cheap
post-load decoder cycles.
With `--ld2`, program mode uses the same `clm_program_decoder` policy as the OS program.

## v2.3 (release candidate): the wide model shape W

W is dim 256, 8 heads of 32, hidden 576, 6 layers, vocab 781, context 256 (`lab/E7.md`). The
port vehicle is E7's `runs/e7/export/W-s11`. Any export of that shape loads in the W build,
with its own CLMVOC and LD2 fit, so a model chosen after E9 needs no program change.

**Build per shape.** The core is still compiled for one shape. `core/clm_shape_w.h` (from
`gen_shape.py`) is force-included ahead of `core/clm_shape.h`, whose include guard it shares.
It is selected by `CLM_SHAPE` in `build_core.sh`, `make SHAPE=w` (into `bin/w`, `obj/w` and
`ce/build/calclm-w`), and the export's dims in `ce/tools/clm.py` (`SHAPES`, `shape_tag`).
v2.2's default build is the same machine code as before except the 4-byte CLMCODE build id
(test.bin and clmcode.bin compared byte for byte). Its CEmu cycles are unchanged: seed 19 is
20,124,918,310 cycles, as shipped.

**What W changed.** One loop in `clm_fwd.c` ran a `uint8_t` over the 256 query entries; it now
uses a 16-bit index for W only. Everything else was already generic or the same size:
- MQA keeps one 32-wide K/V head, so the K cache (BSS), the V cache (CLMTMP) and the attention
  routines are unchanged;
- the matvec kernels are generated for G = 52 and 116; even G gives one row per pass instead
  of two, so the code is smaller;
- `CLM_ACT_BYTES`, the table bank columns and `CLM_MAX_APPVARS` (exactly 16) all fit.

The emulator harness places W's larger debug taps and its V cache lower in RAM; v2.2's
addresses are unchanged.

**Accumulator bound.** `INTREF.md`'s |acc| ≤ 127 n_in < 2^16 holds for any weights only up to
n_in = 516. W's w2 has 576 inputs. The real bound is 127 times a row's nonzero weights.
W-s11 has at most 403 per w2 row, so |acc| ≤ 51,181. Over 26,927 val positions, w2 peaked at
3,839. `ce/tools/stage_export.py` refuses an export whose bound reaches 2^16; the scale_out
assembly and intref both assume it.

| user RAM: expanded program | 58,821 | 60,999 | |
| user RAM: CLMTMP, V cache + LD2 workspace | 49,152 + 2,652 | 49,152 + 2,652 | |
| user RAM needed, with the 4 KiB margin | 114,721 + libraries | 116,899 + libraries | free RAM |
| VRAM table bank from 0xD40000 | 0xF2E9 (62,185) | 0xF2CF (62,159) | 0xF300, the activations |
| VRAM activations from 0xD4F300 | 13,011 | 12,177 | 14,080, the flash RAM window |
| archive: model AppVars, data bytes | 16, 996,749 | 11, 677,063 | 65,505 each; W's largest is CLM12 at 65,477 |

**Bit-exactness.** These modules check the W core against intref and the linker in CEmu
(`emu`, `emuflash`) and on the host, with a W core build:
- `test_calclm_w.py`: test_calclm_v2's format 2 tests, imported unchanged;
- `test_calclm_w_horizons.py`: the horizons tests, imported unchanged; horizons are 4..128 for

- `test_calclm_w_ld2.py`: LD2 with W's fit, the CLMLD2 binding, the program's load policy, the

- `test_bundle_w.py`: the bundle and staging.

- Masks: 0.23 M per token, as for v2.

1. stage the new export;
2. fit LD2 on it as above, and add `export_sha256` to the fit, saved as

   machine-readable line. `test_each_w_export_has_its_fit_and_one_check_sheet` fails until each
   W export has a fit on E2b's programs and exactly one sheet.

### v2.3-rc2: E10's L4-s23

rc2 is rc1's W build with the model swapped for E10's adopted candidate, `runs/e10/export/L4-s23`
(`runs/e10/decision.json` "candidate"). L4 is W trained four times longer. Its seed 23 had the
best `task_correct_dev`, 6.45, so that figure is optimistically selected: it was the best of the
arm's 16 decision seeds. The arm means were L4 4.73 and W 3.41 (E10 passed for L4). In E10's
report, the held-out score and the device acceptance check are what confirm the pick; the device
check is this release candidate's sheet. The program and CLMCODE are rc1's, and CLMCODE is
byte-identical. The model AppVars, CLMVOC and CLMLD2 change.

- **LD2 fit** `ce/tests/fixtures/ld2_offsets_L4-s23.json`: W-s11's recipe on the same 2,000
  programs (same `programs_sha256`), `model.linker fit --data data/tok --n-programs 2000
  --horizons --hazard-full --workers 4`, plus `export_sha256`. All 12 non-empty cells fit.
- **Accumulator bound:** L4-s23's w2 rows have at most 394 nonzero weights of 576 (W-s11: 403),
  so |acc| ≤ 127 × 394 = 50,038 < 2^16. `stage_export` accepts it.
- **Tests:** `test_calclm_w.py`, `test_calclm_w_horizons.py`, `test_calclm_w_ld2.py` and
  `test_bundle_w.py` run on each export in `W_EXPORTS` (`ce/tools/clm.py`: W-s11 and L4-s23).
  Each W export's LD2 fit is `fixtures/ld2_offsets_<export>.json`, and its hardware check is the
  `hw/checks/*/CHECK.md` whose line names its export hash.
  `test_calclm_horizons`'s 1024-token test now leaves a final `<eos>` out of the reference
  tracker, as the core does. L4-s23 is the first model whose seeds 1 and 3 end there.
- **Hardware check** seed 20, not 19. On L4-s23, seed 19 writes a degenerate program (474 tokens,
  66 of 72 lines bare one-variable assignments). Seed 20 is the lowest seed from 19 with
  150-600 tokens that writes a real program: 316 tokens, 18 lines.
- **Speed** (CEmu, as rc1's): the check program (seed 20, INSTALL check 3's settings) writes
  316 tokens in 22.51 G cycles, 71.22 M per token, 0.674 tok/s, 7.81 minutes (rc1's W-s11:
  73.08 M, 0.657 tok/s; v2.2: 0.820 tok/s). The cost per token is the shape's; rc2's check is a
  shorter program than rc1's.
- Archive: the model files are 189 bytes smaller than rc1's; all CalcLM files total 1,046,784 B.

### v2.4: safety masks (mask level 2)

v2.4 is rc2 (W build, E10's L4-s23, its LD2 fit) with the logit masks at level 2
(`model/safety.py`, `model/INTREF.md` 13, docs/agents/phase1-safety-masks.md): no `prgm` calls,
no commands that change persistent settings, no stores into window/table/finance variables, and
no credit lines in strings (a word starting with BY, COPYR, `(C)`). `clm_reset`'s `masks` is a
level: 0 off, 1 (`CLM_MASKS_V23`) v2.3's masks, 2 (`CLM_MASKS_V24`); `src/main.c` passes 2 when
masks are on. Level 1 reproduces rc2 exactly (its hardware-check sheet still passes). The
generated tables are in `core/clm_mask_ids.h`; `clm_t` gains one byte (`str_state`).
Tests: `ce/tests/test_calclm_safety.py` (host, CEmu RAM, CEmu flash). Python entry points take
`--mask-level 2` (`model.linker sample`, `lab.e14 sample`, `ce.tools.hw_check`); level 1 stays
their default. Device cost: see docs/agents/phase1-safety-masks.md section 8.

## Build

> **Prerequisites.** The build needs the CE C toolchain (CEdev v15.0,
> https://github.com/CE-Programming/toolchain), installed at `~/CEdev`: `make` runs the
> `cedev-config` on `PATH`, as the command below sets it, and `tools/build_core.sh` reads
> `CEDEV` for another install folder (`tools/build_flash.py` does not). Without the toolchain,
> `make` prints "cedev-config: No such file or directory" and stops at a missing toolchain
> program. The program builds without a model, but the CLMVOC step and most tests need a model
> export, which is not published.

```sh
cd ce/calclm && PATH=$HOME/CEdev/bin:$PATH make     # bin/CALCLM.8xp + bin/CLMCODE.8xv
                                                    # (runs tools/build_core.sh -> ../build/calclm/core.o)
uv run python ce/calclm/tools/make_vocab.py runs/v1/export -o ce/calclm/bin/CLMVOC.8xv
uv run pytest ce/tests                              # everything (about 15 minutes)
uv run python -m ce.tools.clm_bench [--flash]       # cycles per token by position
uv run python -m ce.tools.clm_bench --v2 --flash    # format 2: past the window, mask cost
```

`tools/build_core.sh` alone builds `core.o`, the CEmu test binary and CLMCODE (the tests call it
on demand).

`core/clm_shape.h` holds the model dims the kernels are generated for (d 192, 6 layers, 6 heads
of 32, hidden 512, context 256). The vocab size, the AppVar count and all tensor offsets are
read from the export at run time (vocab up to 1024), so a retrained export with these dims
loads without rebuilding; it needs its own CLMVOC.

| user RAM: AppVar CLMTMP | 49,152 + 2,652 with LD2 | V cache (6 x 256 x 32), then the optional LD2 workspace; smaller cache if RAM is short |
| VRAM 0xD40000-0xD4F2CF | 62,160 | matvec table bank (pages 0..242 x columns 0..206), rebuilt for every matvec |
| VRAM 0xD4F300-0xD52290 | 12,177 | activations (`CLM_ACT_BYTES`) |
| VRAM 0xD52A00-0xD52BFF | 512 | RAM side of the flash-resident routines: statics, kernel variables, 32 jump trampolines |

| archive (v2) | 677,899 + 7,638 + 10,429 | format 2 export: CLM00..CLM10 (no position table), its CLMVOC, CLMCODE |

User RAM needed while running: roughly 115 KiB plus libraries with LD2 (expanded program
about 59.5 KiB + CLMTMP about 50.6 KiB + 4 KiB kept free). If less is free, the context window shrinks to what fits (generation then stops
when the cache is full, as a prefix of the full-context output, for either format: format 2
slides only over the full 256-entry cache; the window is a multiple of 8); below 32 tokens of
context it refuses to run. LD2 reserves its workspace before choosing the context, retaining
the 4 KiB margin. Without accepted offsets, allocation is exactly the old V-cache budget.
An initial validation load uses activation scratch for E and a placeholder V pointer, which
validation never dereferences. After allocation, the loaded model adopts the real cache pointers and context; no extra
model scan is needed. `model_prepare` reloads after graphx clears VRAM and after a saved
program moves RAM variables. Each reload copies E into the current CLMTMP tail.

The K and V caches hold k + 128 and v + 128 so all attention products are unsigned 8 x 8 `mlt`s;
each K row also stores -128 x sum(k + 128) so q . k = sum((q+128)(k+128)) + row term + head term
exactly.

## Speed (CEmu, 48 MHz, LCD DMA on, weights in archive)

cycles (`uv run python -m ce.tools.clm_bench [--flash]`, raw numbers in

included) runs in place from archive, where CEmu's serial-flash cache makes opcode fetches about

A full 255-token program averages about 50.7 M cycles per token with CLMCODE (about 0.95
tokens/s, 4.5 minutes), interpolated from this table; measured in one run (v2 build, format 1,

How the non-matvec cost came down (position 0 / 64, RAM code unless noted):

| step | cycles/token |
|---|---|
| C core (int32 arithmetic through libcrt helpers) | 230 M / 380 M |
| + asm quant_vec, scale_out | 131 M |
| + asm RMSNorm and SwiGLU passes | 78 M / 230 M |
| + asm attention (unsigned 8 x 8 `mlt` MACs on the biased caches) | 72 M / 82 M |
| + asm SiLU, peak scans, embedding; leaner top-k; P.V on compacted nonzero rows (softmax weights are 60-90% zero late in the window) | 67 M / 72 M |
| + flash-resident routines (CLMCODE) | 44 M / 47 M |

What is left besides the kernels (24.4 M): per-row/per-element assembly that is already a
16 x 16 `mlt` product plus rounding per element (scale_out 5.2 M, requant/RMSNorm 7.5 M), the
attention MACs (32 per key per head, 15.9 M at position 255), and some C glue (PF scalars,
sampling). Each remaining item is a few percent; gains have flattened.

## Tests

`uv run pytest ce/tests` (about 15 minutes; `-m "not slow"` skips the 256-token runs and v2's
300- and 600-token runs):

* `test_calclm.py` (138 cases per export, run for v1 and v0): AppVar and header validation
  (count, magic, index, slices, version, dims, vocab, sizes, splits incl. an AppVar boundary
  between a matrix's row scales and exponents, table invariants, memory), residuals after every
  sublayer and logits at step 0, logits over a sequence, token-for-token generation for 7 sampler
  settings (greedy, top-k 1..64, T 0.13..256, seeds 0, 1, 7, 42, 2463534242, 2^32-1), a run that
  ends with `<eos>`, a reduced context (prefix), reset, a full 256-token window, and the CLMCODE
  loader (rejects bad payloads; attach/detach give identical tokens). Backends: host (gcc,
  UBSan), emu (the eZ80 core.o in CEmu, routines in RAM), emuflash (CLMCODE attached).
* `test_calclm_v2.py` (38 cases per backend, format 2 on `runs/v2/export`): format 2 header
  checks (unknown format, NoPE, lut_max range, the ALiBi penalty bound at 2^22 and that it
  does not apply to format 1), residuals and logits at step 0, logits at every position of a
  whole val program through the ring (emulator: around the wrap), also with lut_max 500 and
  129 (not multiples of 2^e), token-for-token generation for 8 sampler settings with masks on and off up to a
  300-token cap, a run that ends with `<eos>`, runs of 300 and 600 tokens (masks on and off,
  slow), the tracker state after a masked generation (byte for byte against the host tracker),
  a smaller cap and a smaller cache (prefixes), the default cap within the token buffer, mask
  decisions against `model/intmask.py` on val program prefixes (lists, strings, matrices),
  at every position inside list names, after Str/matrix tokens and where only `<eos>` is left,
  and on 1024-token generated programs, masks refused for another vocab, the pending-read rule
  on synthetic prefixes, and INSTALL.md's hardware check (seed 89, 476 tokens) as the core's
  own output (slow).
* `test_calclm_asm.py`: every assembly routine against Python models of the INTREF operations,
  with random inputs over every shift amount the routine accepts and the clamping edge cases,
  both as linked in RAM and executing from emulated flash.
* `test_calclm_program.py`: CLMVOC for each export, the 8xv writer, CALCLM.8xp build/size/BSS,
  and that the deployed CLMCODE.8xv is the tested payload.
* M2's `test_kernel.py` still passes unchanged.

An independent review of the core against INTREF.md found one high-severity issue (the
scale_out/t3 assembly assumed each matrix's exponents directly follow its row scales in the
blob; an export cut between them would have been wrong on the calculator only) and smaller
ones (P.V reading up to 7 rows past a V cache whose size is not a multiple of 8, unchecked table
invariants, a scratch write below the scores buffer, an unguarded `clm_forward`, CLMVOC accepted
in RAM). All are fixed and covered by tests; its fuzzing of the primitives and fallbacks found
no bit mismatches.

The v2 port had its own independent review. It found no bit-exactness defect (it checked
the ALiBi run splitting by brute force over lut_max, sh, e, slot and key count). From its
findings: tests for lut_max values that are not multiples of 2^e (a floor-for-ceil mutant
passed the earlier tests), emulator coverage of the list-name mask rules, the ALiBi load bound
at its edge, the CLMVOC vocab hash check before the masks, masks off by default for v1 models,
and the length shown as what the cache allows.

## Verified in emulation vs only on hardware

Verified in CEmu (debugger-style: the CPU is pointed at the test driver; TI-OS launches nothing):
the inference core and its assembly, i.e. the exact `core.o` that CALCLM links, with the AppVars
in emulated flash and buffers at the program's addresses; AppVar/header validation; the flash
copy and its loader; timing. Only on hardware: everything in `src/` (finding the AppVars with
fileioc, the CLMTMP AppVar, graphx screen setup at 0xD52C00 and the custom font, keys, tokens/s
from the hardware timer, saving prgmGEN), CEmu's timing model itself (flash cache, LCD DMA), and
whether the archive area executes code on the device as CEmu does.
