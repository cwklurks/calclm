# CalcLM corpus (M1)

TI-BASIC programs for the TI-83 / 83 Plus / 84 Plus / 84 Plus C SE / 84 Plus CE family, tokenized per SPEC.md. Generated by `corpus/report.py`; numbers below are from the data on disk when it last ran.

## Verdict: GO

- **55,835,585 train tokens** in 41,389 programs (+ 1,033,655 val tokens in 666 programs) after exact dedup and filtering.
- That is **22.3 tokens per ternary weight** for the ~2.5M-weight v0 model. Chinchilla-style compute-optimal training wants roughly 20 tokens per parameter (~50M token-passes for 2.5M weights), which this corpus covers in ~0.9 epochs; even a 5-10x over-trained small model (250-500M token-passes) is 4-9 epochs. Ternary/QAT models need more tokens than fp ones, which this also allows. The bar in the brief (>= ~5M tokens workable, < ~1M not) is cleared by a wide margin.
- Caveats that matter more than raw size: (1) **67.2% of programs are longer than the 256-token context** (median 512 tokens), so M3 must train on windows and the model will mostly see program middles, not whole programs; only 1,644,043 tokens (2.9%) live in programs that fit in one context. (2) Near-duplicates (versions, ports, level packs): MinHash finds 2,725 clusters holding 3,816 redundant programs / 6,847,897 tokens (12.0%) beyond the longest member of each cluster, so effective diversity is lower than the raw count. (3) 31.5% of tokens are characters inside string literals (menus, text, sprite/level data), cheap for the model but low in program structure. (4) The 2014 ticalc snapshot supplies 68.9% of unique tokens; programs that need 84+CSE/CE tokens (color, `toString(`, `eval(`) are 1,834 programs / 6,375,889 tokens (11.2%), so most training signal is monochrome-era TI-BASIC that still runs on the CE.

## Dedup and split

- Kept program variables (all sources, pre-dedup): 57,143
- Exact duplicate bodies removed (sha1): 15,088
- Unique programs: 42,055 (0 identical to an author eval program were removed)
- Near-duplicates (reported, kept): 313 groups / 661 programs share var name and byte length with a different body; 88 groups / 177 programs are identical after removing spaces, `:` separators and optional closing `)`/`"` at line ends.
- Near-duplicate clusters (MinHash, 64 permutations, 16 bands, 5-token shingles, estimated Jaccard >= 0.7, unioned with the normalized-hash groups): 2,725 clusters with 6,541 programs; 3,816 programs / 6,847,897 tokens beyond the longest member of each cluster. Largest clusters: [23, 20, 18, 17, 16, 15, 15, 15, 14, 13]. Typical members: version series of one game, level files, per-game cleanup programs. They are kept in train (not removed).
- Split (by program, never by token): exact-deduped programs are unioned into 14,275 split groups by normalized body, MinHash Jaccard >= 0.5 and same top-level upload (one ticalc file, one TI-Planet entry or one GitHub repo; largest groups [6247, 369, 352, 333, 292]). A group goes to val iff sha1("1234:" + its smallest member sha1) % 1000 < 30 and it has <= 60 programs, so membership depends only on the group's content and stays stable when the corpus grows. A containment pass then moved 47 val groups to train because one of their programs had >= 30% of its 16-token windows inside a single train program (windows shared by > 200 train programs, i.e. generic boilerplate, are not counted). Exact, normalized, cluster and group keys never straddle train/val (asserted in build.py before writing). Val = 1.6% of programs.

- asm: body starts with a native/hex-asm header (BB6D, BB6C AsmPrgm, EF7B, EF7A Asm84CEPrgm, EF69, EF68 Asm84CPrgm, EF6D), optionally after leading `:`. Covers 83+/84+ shell programs, CE C/ICE/asm binaries and hex-asm sources.
- asm_hex83: TI-83 hex-asm programs (end in `End` / `0000` / `End`).
- undecodable: more than max(2, 0.5%) of tokens are undefined in the TI-84 Plus CE sheet (binary data, other-model vars, corruption).
- trivial: fewer than 8 tokens.
- Protected programs (type 0x06) are kept when they decode (protection is only an edit lock).

## Files

- `corpus/vocab.json`: token list (index = id, uppercase hex), ids 0-3 specials.
- `data/tok/train.bin`, `data/tok/val.bin`: little-endian uint16 ids, programs concatenated as `<bos> tokens <eos>`, program order shuffled (seed 1234).
- `data/tok/eval_author.bin`: The author's programs, same format, eval only.
- `data/tok/programs.jsonl`: one row per program: split, offset (in ids, at `<bos>`), length, sha1, source(s), name, file, member path, tags, n_tokens, n_string_tokens, near_dup_group (MinHash cluster), split_group, min_model.
- `data/tok/meta.json`: vocab size, specials, split seed, counts.
- `data/extract/programs.jsonl`, `files.jsonl`: every program variable found with filter status; per-file extraction events.
- `data/raw/<source>/`: downloads, crawl.log, manifests.

## Reproduce

```sh
cd <repo>
uv run python -I corpus/fetch_warc.py      # ~290 MB of range reads from archive.org, ~5 min
uv run python -I corpus/fetch_ticalc.py    # ~1.2k files, ~25 min at 1 req/s
uv run python -I corpus/fetch_tiplanet.py  # ~1.7k entries, ~1.5 h at 1 req/s
uv run python -I corpus/fetch_github.py    # ~3.7k repo trees + blobs, ~1.5-2 h
uv run python -I corpus/extract.py         # seconds, 24 worker processes
uv run python -I corpus/build.py           # vocab, split, bins (~1 min)
# after M3 has trained on a vocab: keep its ids, only append new tokens
uv run python -I corpus/build.py --freeze-vocab
uv run python -I corpus/report.py          # this file
uv run pytest corpus/tests -q
```

The val split is chosen per group by a content hash, so rebuilding with more data keeps almost all existing val programs in val (groups only change where new programs join them).

All fetchers are resumable (append-only logs, skip finished work). Long ones can run detached: `systemd-run --user --unit=calclm-<source> --working-directory=$PWD uv run python -I corpus/fetch_<source>.py`; progress in `data/raw/<source>/crawl.log`, a final `DONE` line marks completion. Then rerun extract, build, report.

## Open problems

- 54 zip members use pre-deflate methods (implode/shrink) that Python's zipfile cannot read; 63 RAR/7z/StuffIt archives are skipped.
- Programs stored as text (.txt, .8xp.txt, SourceCoder exports) on GitHub are not tokenized; a tivars text-to-token pass could add more (tokenization of text is ambiguous, so keep it separate if added).
- Library heuristics (lib_calls) are approximate; `det(`/`sum(` with a numeric literal first argument is assumed to be a Celtic/DCS call.
- Long programs: most programs exceed the 256-token context; M3 should decide between random windows, program-start-biased windows, or a longer context.
- Near-duplicates are clustered (for an honest split) but not removed; down-weighting large clusters during training is an M3 choice. Variable-rename-invariant matching is not done.
